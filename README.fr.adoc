= clevis-zfs
:toc: left
:toclevels: 2
:source-highlighter: rouge

image:https://github.com/aloli-crystal/clevis-zfs/actions/workflows/ci.yml/badge.svg[CI,link=https://github.com/aloli-crystal/clevis-zfs/actions/workflows/ci.yml]

Client Tang + driver ZFS native encryption pour FreeBSD :
**déverrouillage automatique au boot** des datasets ZFS chiffrés
via le protocole Tang (Network-Bound Disk Encryption — NBDE).

Successeur de https://github.com/aloli-crystal/crystal-clevis-geli[crystal-clevis-geli],
qui utilise le chiffrement natif ZFS au lieu de GELI pour
bénéficier de la **compression avant chiffrement** et des
**sauvegardes chiffrées portables via `zfs send -w`**.

Version anglaise : link:README.adoc[README.adoc].

== Pourquoi ZFS native encryption (et pas GELI) ?

* **Performance** : la compression ZFS s'applique *avant* le
  chiffrement. Sur des données compressibles (logs, BDD, JSON,
  code), 2-5× moins de données à chiffrer — gain CPU et I/O.
  Avec GELI, ZFS voit du bruit cryptographique et la compression
  devient inutile.
* **Boot plus simple** : un seul `zpool import` + `zfs load-key`
  au lieu d'une chaîne `geli attach × N` + `zpool import × N`.
* **Sauvegardes portables** : `zfs send -w` exporte les snapshots
  chiffrés tels quels, ce qui permet des backups off-site via des
  relais non-confiance sans jamais exposer la clé.

== Architecture

[source]
----
                  ┌────────────────────────────────────┐
                  │     clevis-zfs (this)      │
                  │                                    │
                  │  bind / unlock  ── zfs load-key    │
                  │  Tang HTTP/JOSE                    │
                  └─────────────┬──────────────────────┘
                                │
                                │ HTTP + JOSE
                                ▼
                       ┌────────────────┐
                       │ Serveur(s) Tang│
                       │ (pkg FreeBSD)  │
                       └────────────────┘
----

== Utilisation

[source,shell]
----
# Lier un dataset ZFS à un serveur Tang (crée le dataset chiffré)
clevis-zfs bind --init \
    --dataset zroot/zsys \
    --tang http://tang-nas.local:8888

# Au boot (depuis rc.d) :
clevis-zfs unlock --dataset zroot/zsys
----

== État

* **v0.1** : bind/unlock single-Tang sur un dataset ZFS. Protocole
  Tang sur `jose`. Primitives JOSE validées contre
  `latchset/jose`.
* **v0.1** : chiffrement natif ZFS (keyformat=hex, keylocation=prompt
  via stdin, jamais en argv).
* **v0.1** : rc.d pour déverrouillage automatique au boot (après
  `NETWORKING`, avant `mountcritremote`).
* **v0.2** ✅ : CLI multi-Tang via Shamir Secret Sharing
  (`--tang URL` répétable, `--threshold K`). La sous-commande
  `unlock` détecte automatiquement le format single-Tang ou SSS
  depuis l'en-tête JWE.
* **v0.2** ✅ : `bind --use-existing-key` pour migrer un dataset
  déjà chiffré (`mode: ssh_unlock` → `mode: tang`) sans réécrire
  les données.
* **v0.2** ✅ : prend en charge **les trois sérialisations JWS de
  RFC 7515** pour les advertisements Tang (Compact, Flattened
  JSON, General JSON avec tableau `signatures[]` — émis par le
  démon `tangd` FreeBSD après `tangd-rotate-keys`).

== Testé dans une vraie VM FreeBSD

Le dépôt fournit un **banc QEMU scripté** (macOS Apple Silicon)
sous link:examples/qemu-lab/[examples/qemu-lab/]. Deux VMs
FreeBSD 15 aarch64 (serveur Tang + client ZFS), huit scripts
shell numérotés, ~10 minutes du démarrage à froid jusqu'à une
validation end-to-end complète.

Le banc couvre :

[cols="2,3", options="header"]
|===
| Scénario | Résultat attendu

| Single-Tang `bind --init` + `unlock`
| Dataset ZFS chiffré (AES-256-GCM, lz4) créé puis ré-attaché
  après `zfs unload-key`.

| Multi-Tang K=2/N=3 `bind` + `unlock`
| Le JWE contient le claim `clevis.sss` avec 3 sub-JWE ; unlock
  avec les 3 Tangs disponibles.

| Tolérance : couper 1 Tang sur 3
| `unlock` continue à fonctionner.

| Échec : couper 2 Tangs sur 3
| `unlock` échoue proprement avec `recovered only 1 / 2 required shares`.

| Reboot de la VM
| `rc.d/clevis-zfs` déverrouille automatiquement les
  deux datasets en ~20 secondes ; les datasets enfants se
  montent ; les I/O fonctionnent.
|===

Pour le rejouer vous-même :

[source,shell]
----
cd examples/qemu-lab/
./00-fetch-image.sh         # télécharge l'image cloud FreeBSD 15
./01-prepare-disks.sh       # clone les disques, génère les seeds cloud-init
./10-run-tang.sh            # démarre la VM Tang
./11-run-client.sh          # démarre la VM client ZFS
./20-provision-tang.sh      # installe tang, lance 3 instances tangd
./21-provision-client.sh    # build + installe le binaire
./30-test-bind-unlock.sh    # 4 scénarios de test, exit code != 0 si échec
./99-stop-all.sh            # arrêt propre
----

== Installation

[source,shell]
----
shards install
shards build --release
sudo install -m 0755 bin/clevis-zfs /usr/local/sbin/
sudo install -m 0755 etc/rc.d/clevis-zfs /usr/local/etc/rc.d/
----

Puis dans `/etc/rc.conf` :

[source,shell]
----
crystal_clevis_zfs_enable="YES"
crystal_clevis_zfs_datasets="zroot/zsys zroot/zdata zroot/zsave"
----

== Discipline de la clé en mémoire

* La clé n'est **jamais** passée en argument de commande shell
  (visible dans `ps`).
* La clé n'est **jamais** mise dans l'environnement d'un sous-processus.
* La clé est passée à `zfs(8)` via stdin, puis le pipe est fermé.
* La `String` Crystal portant la clé est **scrubbed** (écrasée par
  des zéros) avant d'être rendue au GC.
* Le JWE sur disque ne contient **pas** la clé en clair : il
  contient l'enveloppe McCallum-Relyea, qui ne peut être ouverte
  qu'en collaboration avec le serveur Tang.
